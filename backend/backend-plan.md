# 校园二手交易平台后端搭建计划

本计划面向数据库课程实践，优先做出能够与前端联调、完整演示交易流程的后端。采用 Spring Boot + 原生 MyBatis + MySQL，业务 SQL 手写并保存在 XML 中。先完成单体应用，不引入微服务、Redis、消息队列或真实支付。
主要业务模块已编写并完成后端规则与接口测试；按用户指定的修正口径处理数据结构，真实 MySQL 和前后端联调尚待完成。详细边界见 backend/README.md。

已核对以下仓库材料：

- 同目录 `secondHandTrasaction_sws/` 中的 CDM、PDM、BPM：通过模型 XML 核对实体、关系、字段与业务加工节点，未使用 PowerDesigner GUI 检查图形布局。

系统设计明确了七个业务实体：用户、分类、商品、订单、评价、私信、举报。第一版沿用这一主体，但文档、模型与导出 SQL 尚未完全一致，不能直接以导出脚本作为接口和实体类的最终依据。

## 2 第一版范围

### 先完成可演示的交易闭环

1. 学生注册、登录、退出，查看和修改自己的基础资料。
2. 卖家发布商品，提交后进入待审核；查看自己的商品和驳回理由。
3. 管理员审核通过或驳回商品，维护商品分类。
4. 买家按关键词、分类、价格筛选商品，分页浏览和查看详情。
5. 买家下单，执行演示用模拟支付；卖家确认交付，买家确认完成。
6. 买家可取消未支付订单；完成后可提交一次评分和评价。

原设计没有商品封面字段，当前不增加封面或图片上传功能。交易先演示校内自提，邮寄地址、物流和售后另排；交易方式沿用原模型的 1邮寄、2自提、3两者，优先演示自提；不接入物流追踪。

### 闭环稳定后补齐设计要求

- 私信：发送消息、查看与指定用户的历史消息、接收方标记已读。使用普通 HTTP 请求和简单轮询，不做 WebSocket。
- 举报：用户举报指定商品；管理员查看列表、填写处理结果。需要下架时显式执行下架操作。
- 管理端简单统计：商品分类数量、订单数量和已完成交易金额，用于课程展示。

收藏、求购、密码找回邮件、搜索联想、SMTP、站点初始化向导、复杂仪表盘暂不纳入第一版。它们部分只出现于前端 README，且现有七表不能完整支持，需由项目管理同学另行确认需求。

## 4 后端工程组织

建议 JDK 17 + Spring Boot 3.5.x + MyBatis Spring Boot Starter 3.0.x + Maven + MySQL 8.0。具体补丁版本在创建工程时锁定。MyBatis 官方兼容说明列明 Starter 3.0.x 对应 Java 17+、Spring Boot 3.2～3.5：[官方说明](https://github.com/mybatis/spring-boot-starter)。

依赖只放 Spring Web、Validation、Spring Security、MyBatis Starter、MySQL Connector/J 和 Spring Boot Test。明确不使用 MyBatis-Plus、JPA 或自动 CRUD 生成替代业务 SQL。

```text
backend/
  pom.xml
  src/main/java/<项目包名>/
    Application.java
    common/                 统一响应、异常、分页
    config/                 安全、MyBatis、静态文件配置
    auth/                   登录注册、当前用户
    user/ category/ goods/ order/ evaluate/ message/ report/
      controller/           HTTP 参数与响应
      service/              业务规则、权限和事务
      mapper/               MyBatis 接口
      entity/               数据表映射
      dto/                  请求字段
      vo/                   返回前端的数据
  src/main/resources/
    application.yml
    mapper/                 UserMapper.xml、GoodsMapper.xml 等
  src/test/                 核心交易规则与 MySQL 集成测试
db/
  schema.sql                DBA 确认后的建表、约束和索引
  queries-demo.sql          答辩使用的查询与 EXPLAIN
```

Controller → Service → Mapper → MySQL。Service 暂时直接写具体类，无需为每个类再创建只有一个实现的接口。多表联查直接由 Mapper SQL 返回 VO，不在 Java 中逐条循环查询关联表。

认证建议使用 Spring Security Session，登录后刷新会话标识，密码使用 BCrypt 单向哈希。前端经 Vite `/api` 代理携带 Cookie，并按约定获取、发送 CSRF token。后端从会话确定用户身份，禁止信任请求里的角色、卖家 ID 或买家 ID。注册接口始终创建学生账号；管理员开通方式另行接入。

数据库密码从环境变量读取。当前头像与举报证据只保存已有地址字段，不实现文件上传或新增商品图片字段。

## 5 交易规则与事务

订单编码已按用户确认沿用系统设计同学的 PDM：0待付款、1待发货、2待收货、3完成、4取消、5售后。商品编码按修正口径采用 Word。下方事务方案仍需与实际触发器行为衔接，避免重复更新。

| 对象 | 状态建议 | 主要流转 |
| --- | --- | --- |
| 商品 | 0可售、1已售、2下架、3待审核、4驳回 | 发布→3；审核通过→0；驳回→4；交易完成→1 |
| 订单 | 0待付款、1待发货、2待收货、3完成、4取消、5售后 | 模拟支付0→1；卖家交付1→2；买家确认2→3；未支付取消0→4；第一版不开放售后操作 |
| 支付 | 若保留 PDM 的 pay_status，则0未支付、1已支付 | 模拟支付时与订单状态在同一事务更新 |

PDM 的状态 5 售后暂不开放。已支付订单暂不支持取消退款。接口和页面应明确提示模拟支付，不处理真实资金。

**下单事务：** 使用 `@Transactional`，先按主键 `SELECT ... FOR UPDATE` 锁定商品行，校验商品可售、买家不是卖家，再以当前读检查该商品是否已有状态 0、1、2、3 的订单；存在则拒绝，不存在才按数据库当前售价创建订单。订单价格是成交快照，用 `BigDecimal`，不接受前端提交金额覆盖。

商品在待交易期间仍保留状态 0，但公开列表和详情通过有效订单计算 `purchasable=false`。锁定商品行的检查也必须用于编辑、下架、审核和所有订单状态变更，避免下单后改价或下架；统一先锁商品再锁订单，降低死锁风险。事务内检查有效订单使用锁定读，不能依赖事务早先建立的普通查询快照。

**取消与完成：** 取消只允许该订单买家对状态 0 操作，取消后商品可重新购买；第一版不做超时自动取消，演示需主动取消占用订单。完成只允许买家对状态 2 操作，同一事务更新订单完成状态和商品已售状态（不新增 Word 中没有的完成时间列）。状态更新带旧状态条件并检查影响行数，重复点击不能重复改变业务结果。

**商品编辑：** 商品所有者可编辑无有效订单的商品，修改后重新进入待审核；已售商品不可编辑。审核驳回必须填写原因。公开列表只展示审核通过且未下架的商品；私有状态详情仅所有者和管理员可访问。

**评价：** 只有已完成订单的买家可评价，评分 1～5，`UNIQUE(order_id)` 防止重复请求产生两条评价。

## 7 SQL 如何体现数据库课程内容

所有业务 SQL 存在 `src/main/resources/mapper/*.xml`，方法名与 Mapper 接口对应。参数使用 `#{...}`，条件使用 `<if>`、`<where>`、`<choose>`；不拼接用户输入到 SQL，不用 `${...}` 接收搜索词或排序列名。

| SQL 类型 | 对应业务与展示价值 |
| --- | --- |
| INSERT、UPDATE、SELECT | 注册、发布、审核，说明增删改查如何服务业务 |
| JOIN | 商品关联分类和卖家；订单关联商品及买卖双方；评价关联订单 |
| 动态 WHERE + LIMIT/OFFSET + COUNT | 商品条件筛选和分页，列表与总数保持相同筛选规则 |
| GROUP BY、SUM、COUNT | 按分类统计商品数、按卖家统计完成订单金额，状态条件防止把取消订单算入成交 |
| NOT EXISTS 或 EXISTS | 判断商品是否存在有效订单 |
| SELECT FOR UPDATE + 条件 UPDATE | 两个买家同时购买同一商品时只有一个成功 |
| 唯一约束、外键与事务回滚 | 重复手机号、重复评价、非法引用、下单失败不留下半条业务数据 |
| EXPLAIN | 比较常用查询计划，解释索引解决了什么问题 |

索引候选由实际 SQL 决定：`goods(goods_status,cate_id,publish_time)`、`orders(goods_id,order_status)`、买家/卖家加创建时间、消息收发人加时间、举报状态加时间。不要把这些全部机械添加；后端提供实际查询，索引效果结合 EXPLAIN 结果判断。`LIKE '%关键词%'` 先用于课程规模数据，不宣称普通 B 树索引可以加速任意包含搜索。

按用户最新安排，等 DBA 完成数据库：有触发器则依实际行为衔接，无触发器则后端不自行新增。当前先用后端事务实现关联更新，之后如需由触发器承担则调整对应代码。

## 10 最少要验证的场景

- 重复手机号注册失败，密码不明文保存；学生不能调用管理员接口。
- 未审核、驳回、下架商品不出现在公开列表，未授权用户无法绕过列表访问详情。
- 用户不能编辑他人商品、读取他人订单、读取无关私信。
- 价格 12.34 元入库和返回一致；分页总数与实际筛选匹配。
- 两个独立用户并发下单同一商品，只有一笔有效订单；重复点击不会重复成交。
- 下单事务中途失败能回滚；存在有效订单时卖家不能改价或下架。
- 未支付取消后可以重新购买；完成后不能再次购买，未完成不能评价，重复评价失败。
- 不存在的分类或商品引用被拒绝，含单引号的搜索词正常作为参数处理。

事务、锁、外键和金额测试使用独立 MySQL 测试库，不以 H2 测试通过代替 MySQL 验证。验收记录区分“已运行通过”和“待验证”。

下一步接入实际 MySQL，验证 SQL、约束、并发与回滚，再做前后端联调。代码暂留本地，按用户要求在联调前再考虑提交推送。
