# 接口请求集合

导入 `secondhand.postman_collection.json` 到 Postman，包含 50 个可选择执行的请求。集合与当前接口实现对应，支持响应断言和业务 ID 自动保存；不会自行创建数据库、账号或演示数据。

## 使用前

1. 基础接口可在 local 模式执行；业务请求需要后端以 mysql 模式连接实际开发数据库。真实数据库执行由 DBA 负责。
2. 在集合变量中设置 baseUrl，并在本地填写所需账号、密码和请求字段。不要把密码保存回仓库或分享导出文件。
3. 使用已有分类时填写 categoryId；只有确需新增分类时才执行新增请求。注册同样是可选请求，不是初始化步骤。
4. 保持 Postman Cookie Jar 开启；一个会话当前只对应一个登录身份。切换身份通过集合中的买家、卖家、管理员登录请求完成。

集合中的写请求会实际改变数据。请手动按场景选择请求，不要直接运行整个集合；通过与驳回、完成与取消属于互斥分支。

## CSRF 与身份

先执行“获取当前会话 CSRF”，响应脚本会设置 csrfToken 与 csrfHeader。写请求自动引用这两个变量。

登录后会话 ID 和 CSRF 会刷新，所以每次登录或退出后都需要重新执行“获取当前会话 CSRF”。集合在登录与退出成功时清空旧 token，防止误用。403 表示权限或 CSRF 问题；先检查当前用户与 token，不要直接认定登录失败。

登录买家和卖家时分别保存 buyerId、sellerId。发布商品、创建订单、发送消息、提交举报会分别保存 goodsId、orderId、msgId、reportId。新增分类保存 categoryId。

## 推荐手动执行顺序

1. 服务状态 → 取 CSRF → 卖家登录 → 再取 CSRF → 当前用户 → 分类列表。
2. 填写分类与商品字段 → 发布商品 → 查看我的商品与商品详情。
3. 取 CSRF → 管理员登录 → 再取 CSRF → 待审核列表 → 按需修改待审核商品 → 审核通过。
4. 取 CSRF → 买家登录 → 再取 CSRF → 公开商品列表 → 下单 → 模拟支付。
5. 切换卖家并刷新 CSRF → 确认交付。
6. 切换买家并刷新 CSRF → 确认完成 → 评价 → 商品评价列表 → 我的评价。

取消订单需另选未支付订单；商品驳回需另选待审核商品；下架需选择没有有效订单且未售出的商品。不要对已完成主流程的同一记录强行执行这些分支。

私信：买家发送给 sellerId → 卖家登录后标记 msgId 已读。举报：提交真实 goodsId，reportType 使用 1至5（假冒伪劣、欺诈行为、辱骂骚扰、违规违禁品、其他）；成功后保存 reportId，管理员可查看并处理，处理不自动下架。

## 请求覆盖与验证范围

集合覆盖当前全部 Controller 路由及 Security 提供的退出接口，含注册登录、资料、分类、商品、审核、订单、评价、私信和举报。

请求体按当前校验规则填写；空白业务变量需要使用者补全。JSON 集合结构和脚本可离线检查，但业务请求尚未在真实 MySQL 和 Postman 中完整执行。打包启动验证见 `../scripts/verify-packaged.ps1`，该脚本只执行无数据库基础检查，不执行业务写请求。

图片上传请求需先在 Postman 的 form-data 中选择本地 JPEG/PNG 文件，登录并获取 CSRF；上传响应会保存 uploadedImageUrl，可接着执行图片访问请求。图片目前不关联商品。改密码请求会改变当前账号密码，请单独执行并更新本地登录变量。
