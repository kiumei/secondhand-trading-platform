# 后端与 DBA 交接

## 职责与交付建议

| 内容 | DBA 与测试 | 后端 |
| --- | --- | --- |
| 表结构 | 提供可运行建表脚本、外键、约束和字段说明 | 按字段编写实体和 Mapper，反馈影响功能的情况 |
| 业务 SQL | 协助审阅查询、约束和索引效果 | 使用原生 MyBatis XML 写增删改查、联查和统计 |
| 事务 | 提供 InnoDB 测试环境，协助复现并发与回滚 | 在 Service 实现事务边界、权限和状态校验 |
| 触发器 | 按课程要求设计并提供触发器定义及其行为说明 | 根据触发器的写入行为和错误条件衔接事务与接口 |
| 验收 | 执行业务、约束、并发测试并记录结果 | 提供接口示例，定位并修复后端问题 |

后端按 DBA 提供的数据库脚本和字段说明接入，业务 SQL 保存在后端 Mapper XML 中。后端启动不自动删除表或重建数据库。

## 数据基础建议

沿用文档中的 MySQL 8.0、InnoDB、utf8mb4。表名采用 sys_user、category、goods、orders、evaluate、message、report，字段名和长度优先遵循 Word 数据字典。

| 约定项 | 建议做法 |
| --- | --- |
| 主键 | 沿用 Word 的 VARCHAR(32)，后端生成无连字符 UUID；引用字段使用相同类型和字符规则 |
| 金额 | 沿用 DECIMAL(10,2)，Java 使用 BigDecimal |
| 时间 | 沿用 DATETIME；建议开发库和后端统一按 Asia/Shanghai 解释，API 输出明确时区 |
| 角色 | 沿用 0 学生、1 管理员；注册接口不能创建管理员 |
| 商品状态 | 沿用 Word：0 未售出、1 已售出、2 下架、3 待审核、4 驳回 |
| 登录标识 | 建议手机号登录并建立唯一约束，昵称允许重复 |
| 评价关联 | 保留 Word 中 order_id、goods_id、evaluate_user_id，由后端根据订单填充并检查一致性 |
| 订单状态 | 沿用 PDM：0待付款、1待发货、2待收货、3完成、4取消、5售后；第一版不开放售后操作 |

订单取消、交付和完成属于拟实现的交易流程，其状态及时间字段扩展待交易模块接入时再落实。原设计没有商品封面字段，本轮不增加该字段。

密码用 BCrypt 哈希保存，不保存明文。后端提供匹配所用 PasswordEncoder 格式的哈希；若使用带算法前缀的编码格式，再检查字段长度是否足够。

DBA 提供 MySQL 实际版本、主机、端口、数据库名、字符集和排序规则。后端通过环境变量连接，应用账号通常只需业务查询与写入权限，建表使用单独的开发管理账号。

## 约束与索引建议

沿用现有主键和外键设计，建议补足必要的 NOT NULL、手机号唯一、评分 1～5、金额非负和状态范围检查。若采用“一笔订单仅买家评价一次”，建议 evaluate.order_id 唯一。CHECK 是否按预期执行，以实际 MySQL 版本的测试结果为准。

建议保留同一商品多条历史订单的能力，不为 orders.goods_id 添加普通唯一约束；一件商品不能同时被多个人购买由后端事务控制。有关联记录的用户、分类和商品不建议级联删除，商品优先通过下架保留交易历史。

后端会提供实际查询，再共同决定索引。首批候选如下：

| 查询 | 可考虑的索引字段 |
| --- | --- |
| 可售商品按分类和时间查询 | goods_status、cate_id、publish_time |
| 我买入/卖出的订单 | buyer_id 或 seller_id，加 create_time |
| 双方私信历史 | send_user_id、receive_user_id、send_time |

## 后端拟实现的事务规则

下单时后端先锁定商品行，检查可售状态、买卖双方身份以及有效订单，再创建订单。售价从数据库商品读取，不能以客户端提交金额为准。

涉及同一商品的编辑、下架和订单动作建议统一先锁商品再锁订单；状态变更携带旧状态条件，检查更新行数。确认完成时订单与商品状态在同一事务更新，失败应全部回滚。订单编码按上表沿用 PDM，关联更新与触发器行为衔接。

评价的商品和评价人从已完成订单确定，后端不信任客户端任意传入关联 ID。唯一约束用于兜底防止重复提交。外键保证关联对象存在，Service 保证操作者确有权限，两者分别验证。

## 触发器交接

按当前分工，等 DBA 完成数据库后，以实际触发器定义为准衔接后端；未定义的触发器不由后端自行新增。若存在触发器，接入时需了解触发的表和事件、关联更新与错误条件。

若触发器负责某项关联更新，后端应避免重复执行同一更新；Service 仍负责请求权限和业务流程。上文所述事务更新方案以实际触发器行为为准，接入后验证回滚效果。
