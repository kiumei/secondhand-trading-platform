## 一、 严重问题 1：主键策略被错误改回 UUID

**冲突说明**：
最新交接文档写道：“主键沿用 Word 的 VARCHAR(32)，后端生成无连字符 UUID。”
但上一版（我方已确认的基线）明确约定：**主键采用当前数据库 INT AUTO_INCREMENT，由 MyBatis 回填；orders.order_id 仍为 VARCHAR(32)**。

**数据库实际事实**：
所有实体表（sys_user, goods, orders 等）的主键均为 **INT AUTO_INCREMENT**。

**潜在影响**：
如果后端强行按 VARCHAR(32) 编写实体类和 Mapper，会导致所有外键关联（如 goods.user_id -> sys_user.user_id）数据类型不匹配，导致联调直接报错。

**要求（需后端确认）**：
主键必须恢复为 **INT AUTO_INCREMENT**；订单号 `order_id` 可保留 `VARCHAR(32)` 由后端生成。

## 二、 严重问题 2：商品状态码被错误改回旧版

**冲突说明**：
最新交接文档写道：“商品状态沿用 Word：0 未售出、1 已售出、2 下架、3 待审核、4 驳回。”
但上一版（我方已确认并已写入数据库的基线）明确约定：**0 待审核、1 上架、2 下架、3 已售出、4 驳回**。文档末尾的触发器交接部分（`trg_order_complete_update_goods`：订单变为3完成时，将商品改为3已售出）也印证了这一点。

**数据库实际事实**：
`goods_status` 字段的实际业务语义及数据库 CHECK 约束均为：**0待审核、1上架、2下架、3已售出、4驳回**。

**潜在影响**：
若后端按“0未售出、3待审核”编写代码，商品审核、上下架、购买流程将彻底反了，前端显示也会出现严重错乱。

**要求（需后端确认）**：
必须严格遵守数据库定义：**0待审核、1上架、2下架、3已售出、4驳回**。

## 三、 严重问题 3：健康检查接口返回 404

**现象**：
使用浏览器访问 `http://localhost:8080/api/health` 时，返回 **404 Not Found**。

**排查结论**：
说明后端服务可能未启动，或者目前以 `local`（本地测试）模式运行，而未以 `mysql`（真实数据库联调）模式运行。

**影响**：
数据库无法连接，导致无法执行后续的接口测试、触发器验证和并发压测。

**要求（需后端确认）**：
1. 请确认是否已配置好环境变量（`DB_URL`、`DB_USERNAME`、`DB_PASSWORD`），并已私聊获取数据库密码。
2. 请务必使用命令启动真实业务模式：`mvn spring-boot:run "-Dspring-boot.run.profiles=mysql"`
3. 请检查启动日志，确认无连接报错，并确保 `http://localhost:8080/api/health` 返回 `data.status=UP`。
